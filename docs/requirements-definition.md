## 2. 概要

### 2.1 事業背景と解く問題

- 事実: 教師・講師・採点担当者は、Microsoft Forms または Google Forms で集めた学生レポートの回答を workbook（`.xlsx`）で受け取り、学生ごとに読んで採点している（SRC-001 §1、§2.1）。
- 事実: 前版アプリ（`dahatake/StudyReport-Evaluator`）は、同じ要求（草案と同一内容。git blob `35e595d` が一致）で実装され、製品 0.8.6 が 2026-10-01 に GitHub Releases で公開済み（SRC-002）。clean-host 試験 CH-01〜06 と本人 login は公開前に未実施（SRC-001 文書情報）。
- 事実: 今回の依頼は、本リポジトリで草案のアプリを実装すること。前版との関係は「後継として置き換える」と決定した（Q-002 2026-10-06）。
- 決定: 再実装の目的は、前版の機能を保ったまま、管理データ（本書と [catalog.md](./catalog.md)）を正本にして、担当者や AI エージェントが入れ替わっても保守できる実装へ作り直すこと（Q-008 2026-10-06）。
- 解く問題: 回答の読み込み・定量化の材料づくりにかかる教師の負担。ただし評点の責任は教師が持ち、AI は定量化の候補を作るだけにする（SRC-001 冒頭注記、§2.2）。

### 2.2 目的

| ID | 目的 |
|---|---|
| G-001 | 教師が、Forms から出力した回答 workbook を元に、学生ごと・設問ごとの定量化の候補（点・理由・根拠）を、手作業で全件を読むより少ない手間で揃えられる |
| G-002 | 配点と最終評点の計算を Excel 数式で透明にし、AI の役割を定量化だけに限ることで、教師が根拠を確かめて自分の責任で評点を確定できる |
| G-003 | 学生の回答と元の workbook を守る（元本不変、送信の最小化、本文をログに残さない、ローカルで完結） |
| G-004 | 数百〜20,000 行の長時間処理を、中断やプロセス終了があっても、完了済みの作業を失わずに再開・完了できる |
| G-005 | Windows 11 x64 の一般利用者が、追加の導入作業なしにアプリを起動し、使い始められる |

### 2.3 受益者・費用負担者・決定権者

- 受益者: 採点担当の教員（P-01）、評価設計担当（P-02）、保守エンジニア（P-03）。間接的な影響を受ける人: 評価される学生（評点の公平性・個人情報の扱い）。
- 費用負担者: GitHub Copilot の利用料は、利用者本人または所属組織の GitHub アカウント・契約が負う（SRC-001 §3.2）。アプリ独自の課金はない。
- 決定権者: 本リポジトリの要求所有者（SRC-001 §22 の Approver と同じ役割）。

| 目的 | 指標 | 測定方法 | 目標値 |

### 2.5 事業妥当性の判定

- 判定: 根拠あり。
- 根拠: 要求所有者が 2026-09-01〜2026-10-05 にかけて機能を継続して承認し、前版を公開している（SRC-001 §22、SRC-002）。再実装の目的と前版との関係、G-001 の目標値が利用者の回答で決まった（Q-002、Q-008 2026-10-06）。
- 残る条件: 採点時間の削減効果（手作業との比較）は測定していないため、効果の大きさは表明しない。G-001 の判定は前版との比較で行う。

### 4.5 用語

| 用語 | 意味 |
|---|---|
| 元本 | 利用者が選んだ入力 `.xlsx`。読取専用で扱い、変更しない |
| 回答行 | 1 学生または 1 提出を表す worksheet の 1 行。識別子は Excel の行番号（`SourceRow`） |
| 設問 | 質問文、主回答列、0 件以上の補助列、配点 `Points`、通常 evaluator、固有評価項目を持つ評価単位 |
| 通常 evaluator | `KNOWLEDGE_COVERAGE`（アプリ所有の指示）または `CUSTOM_PROMPT`（利用者の Prompt）。1 件以上の評価項目（criterion）を持つ |
| 固有評価項目 | 設問ごとに 0 件以上持てる、Prompt 能力等を 0〜1 で評価する項目 |
| 参照回答 | 設問ごとに 1 run で 1 回、AI が質問文から生成する回答。類似度の比較相手 |
| 類似度 | 学生回答と参照回答の表層的な近さ（0〜1）。アプリ内で決定的に計算し、AI を使わない。不正行為の証明ではない |
| run | 「定量化を開始」から完了・取消・失敗までの 1 回の処理。開始時に設定を不変の snapshot に固定する |
| checkpoint | run 中に学生行ごとに保存する `.partial.xlsx`。再開の元になる |
| 技術的失敗 | 認証・通信・timeout・schema 不正・quota 等で AI 結果が得られない状態。0 点ではなく空欄にする |
| 空回答 | 主回答（または固有項目の主値）が空のセル。AI へ送らず 0 とする |
| DIP | 装置非依存ピクセル。100% 表示で 1 DIP = 1 物理ピクセル |
| ペルソナ | 利用者像。アクセス制御の役割とは別 |
| ワークスペース | 1 つの step 画面の中で、一覧・詳細・図・ログなどのコンポーネント（パネル）を配置した作業面 |

## 6. 利用シナリオ

- 主要な流れ（P-01）: EXE を開く → 起動直後に Copilot の認証を自動確認（FR-038）→「1 入力」で workbook を選び、sheet・質問文行・回答範囲・設問と列を確認（FR-001〜FR-005）→「2 採点設計」で配点と評価方法を確認（FR-008〜FR-014）→「3 実行」で model を確かめて「定量化を開始」（FR-015〜FR-023、FR-046）→「4 結果」で一覧・詳細を確認し、必要なら override して別 workbook に出力（FR-035、FR-045、FR-050、FR-052）→ 出力 workbook を表計算ソフトで開いて最終評点を確定（FR-024、FR-026）。
- 代替の流れ: 起動引数で入力と Prompt を事前入力して起動（FR-053、FR-054）。保存済みの採点定義を明示適用（FR-041）。network や login がない状態で、読込・mapping・設計だけ行う（NFR-OPS-001）。
- 中断と再開: 「中断」、アプリの終了、プロセスの強制終了の後、`.partial.xlsx` を指定して条件を検証し、未完了の行から再開（FR-030〜FR-033）。
- 変更と取消: ファイル選択や login の取消は現在の状態を変えない（FR-001、FR-037）。実行中も次回用の設定を編集できるが、現在の run には混入しない（FR-042）。
- 失敗と復旧: 認証が必要、quota 枯渇、入力の変更、出力の検証失敗などを、技術 status と次の行動で示す（FR-022、FR-029、FR-031）。
- 支援への引継ぎ: 利用者は troubleshooting 文書（FR-061）と、本文を含まない job log・error code（FR-043、NFR-SEC-002）を支援者に渡せる。

#### FR-010 設問固有評価項目
- 要求: 各設問は 0 件以上の固有評価項目（special item ID・表示名・対象列 1 件・補助列 0 件以上・Custom Prompt template・有効フラグ）を持てる。AI の値は 0〜1。項目ごとの weight は設けず、設問内の有効項目を等分平均する。主値が空なら AI へ送らず 0、技術的失敗なら空欄にする。
- 状態: 承認済み（依頼 2026-10-06）／依頼原文｜MUST｜上位: G-002｜出典: SRC-001 §5.3
- 受入基準 AC-011: 有効な固有項目 2 件の点が 1 と 0 のとき、設問の固有率が 0.5 になる。主値が空の行では AI 送信が 0 件で値が 0、技術的失敗の行では空欄になる。

#### FR-011 Prompt の placeholder 検証
- 要求: 利用者が編集できる通常 Custom evaluator と固有評価の template で使える placeholder は `{設問}`・`{回答}`・`{補助情報}`・`{評価項目}`・`{最小点}`・`{最大点}` の 6 件だけとする。通常 Custom では `{回答}` と `{評価項目}` が必須、固有評価では `{回答}` が必須。literal の波括弧は `{{`・`}}` で escape する。未知の placeholder・閉じていない括弧・不正な escape は AI 送信前に拒否し、挿入した値を再走査しない。Knowledge の template と参照回答・類似度の Prompt はアプリ所有で、利用者は編集できず、`{参照回答}` を利用者向けに公開しない。
- 状態: 承認済み（依頼 2026-10-06）／依頼原文｜MUST（Prompt injection と誤送信の防止）｜上位: G-002、G-003｜出典: SRC-001 §5.4
- 受入基準 AC-012: `{未知}`、`{回答`、`}` 単独を含む template は実行前に拒否され、AI 送信が 0 件。`{{回答}}` は文字どおり `{回答}` として送られる。回答本文に `{設問}` が含まれても再置換されない。

#### FR-012 配点の不変条件
- 要求: 有効な定義は「ベース点 + 固有設定配点 + 有効設問の配点の合計 = 100」を満たす。`Points` は 0 以上の有限数。比較は decimal の厳密値で行い、表示の丸めで判定しない。満たさない定義では run を開始せず、明確な検証エラーを表示する。
- 状態: 承認済み（依頼 2026-10-06）／依頼原文｜MUST（評点の整合）｜上位: G-002｜出典: SRC-001 §6.1、§6.3-5、§16-4
- 受入基準 AC-013: 60 + 0 + 13.333333 + 13.333333 + 13.333334 は開始でき、60 + 0 + 20 + 19.9999999 は開始できず合計不一致のエラーが表示される。

#### FR-013 初期配点と均等配分

#### FR-021 類似度のローカル計算
- 要求: 各回答行の各有効設問について、学生回答と参照回答の表層類似度を、AI を使わずアプリ内で決定的に 0〜1 で計算する（NFKC 正規化・invariant 小文字化・空白と句読点と記号の除去、文字 n-gram は原則 3・短文は 2／1、`max(0.70×学生n-gram包含率 + 0.20×Dice + 0.10×Jaccard, 最長共通部分文字列の被覆率)` を 4 桁に丸める）。学生回答が空なら 0、参照回答が空欄なら空欄。理由は指標値だけの機械生成文で、学生の本文を含めない。同じ設問の他学生との最大類似度と相手行は情報列として出力し、採点式・減点に使わない。類似度を不正行為の証明として表示しない。

#### FR-022 再試行と失敗の扱い

- 要求: 空回答は 0 点相当、技術的失敗は空欄とし、通常評価・固有評価・参照回答・類似度のいずれかが技術的失敗で空欄なら、その行の `Final_Raw` と `Final_Score` も空欄にする。

### 7.4 Excel 計算と出力

#### FR-024 Excel 数式による得点計算
- 要求: 出力 workbook は次を Excel 数式で計算する。`QuestionEarned_q = P_q × R_q`（`R_q` は 0〜1 の通常評価率。criterion の正規化値 0〜100 は 100 で割る）、`SpecialQuestion_q`（設問内の有効固有項目の平均）、`SpecialEarned = S × Σ SpecialQuestion_q / M`（M は有効固有項目を持つ有効設問の数。S = 0 なら 0。固有項目または対象設問に技術的失敗が 1 件でもあれば空欄）、`SimilarityPenalty_q = P_q × L_q × W`（類似度と減点は通常評価とは別の列）、`FinalRaw = B + Σ QuestionEarned_q + SpecialEarned − Σ SimilarityPenalty_q`、`FinalScore`（`FinalRaw` を 0〜100 に clamp）。`W = 0` でも参照回答の生成と類似度の計算を省かない。

### 7.5 checkpoint と再開

#### FR-030 checkpoint の作成と保存

- 状態: 承認済み（Q-001 2026-10-06。提案の範囲を固定部分の除外に修正して承認）／利用者決定｜優先度: SHOULD（CON-UI-01 の中核。理由: 利用者によって一覧・詳細・図の重要度が違い、固定配置では P-01 と P-03 の両方に最適にできない）｜上位: CON-UI-01、G-001｜出典: SRC-003
- 期待する価値: ペルソナと作業ごとに必要な情報を同時に見られる。負担・副作用: 既存の固定レイアウト契約（NFR-UX-001）と Automation ID の再設計、試験の増加。確認方法: 下記 AC。
- 受入基準 AC-079: 「4 結果」で詳細パネルを図のパネルのタブにまとめ、一覧パネルを最大化して元に戻すと、各パネルの内容と選択行が保たれる。

#### NFR-UX-004 レイアウトの保存と復元
- 要求: 変更したレイアウトは、OS 利用者 × 画面（各 step と各設定カテゴリ）の単位で、`setting.txt` とは別の `layout.json`（OS の LocalApplicationData 配下 `StudyReportEvaluator/`）に、変更のたびに自動で保存され、次に開いたときに復元される。`layout.json` にはパネルの配置・大きさ・表示状態だけを入れ、学生の情報・パス・回答・Prompt を入れない。ファイルが壊れている・読めない場合は、ファイルを変更せずに無視し、既定のレイアウトで起動する。プライバシー文書に `layout.json` の保存場所と内容を書く。
- 状態: 承認済み（Q-003 2026-10-06）／利用者決定｜優先度: SHOULD（毎回の再配置は手間になり、変更機能の価値を失わせる）｜上位: CON-UI-01｜出典: SRC-003
- 関連: FR-040（`setting.txt` の schema と明示保存の原則は変えない）、NFR-SEC-004
- 受入基準 AC-080: 「4 結果」のレイアウトを変更してアプリを終了・再起動すると、同じ画面のパネル配置・大きさ・表示状態が復元され、`setting.txt` の bytes は変わらない。`layout.json` を壊れた内容に置き換えて起動すると、既定のレイアウトで起動し、`layout.json` の bytes は変わらない。canary 文字列を入れた run の後、`layout.json` に canary が 0 件。

#### NFR-UX-005 既定のレイアウトへの復元と作業状態の保持
- 要求: 利用者はいつでも 1 操作で既定のレイアウトに戻せる。レイアウトの変更・復元で、入力中の内容・選択中の対象・絞り込み・ページ・実行中の run が失われない。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD（配置を崩しても戻れる安心がないと変更機能が使われない）｜上位: CON-UI-01、G-004｜出典: SRC-003（Restore Defaults）
- 受入基準 AC-081: 設問文の入力途中に「既定のレイアウトに戻す」を実行しても、入力中の文字列・選択設問・ページが変わらない。

#### NFR-UX-006 ドラッグ以外の操作手段
- 要求: ドラッグで行えるパネルの移動・大きさの変更・タブへのまとめは、ドラッグなしの手段（パネルのメニュー、キーボード、コマンド検索）でも行える。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: MUST（NFR-UX-003 を採用する場合。運動機能に制約のある利用者を排除しないため）｜上位: CON-UI-01、NFR-A11Y-001｜出典: SRC-004（WCAG 2.2 SC 2.1.1、SC 2.5.7）
- 受入基準 AC-082: マウスを使わずに、パネルの移動・大きさの変更・タブへのまとめ・最大化・既定への復元をすべて実行できる。

#### NFR-UX-007 コマンド検索とキーボードからの到達
- 要求: 利用者は、キーボードで開くコマンド検索から、step の移動・設定カテゴリの表示・パネルの表示切替・表現の切替・「Copilot 状態を確認」・既定のレイアウトへの復元などの操作を名前で検索して実行できる。よく使う操作（step 移動、開始、中断）にはキーボードの操作を割り当てる。コマンド検索から AI 評価・login を、確認なしに直接開始しない。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD（設定カテゴリとパネルが多く、目で探す手順を減らせる）｜上位: CON-UI-01、G-001｜出典: SRC-003（コマンドパレット）
- 受入基準 AC-083: コマンド検索で「既定」と入力すると「既定のレイアウトに戻す」が候補に出て、Enter で実行できる。コマンド検索の操作だけで AI 送信が始まらない。

#### NFR-UX-008 狭い画面と高い拡大率での縮退
- 要求: ビューポートが狭いときや拡大率が高いとき、パネルは横並びから、タブへのまとめ、縦の積み重ねの順に縮退し、どの状態でもすべてのパネルの情報と操作に到達でき、横スクロールを強いない。縮退は利用者の保存したレイアウトを書き換えない。[ASSUMPTION AS-006] 縮退の閾値。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: MUST（NFR-UX-003 を採用する場合。NFR-UX-001 の到達性を守るため）｜上位: CON-UI-01、NFR-UX-001｜出典: SRC-004（SC 1.4.10）、SRC-001 §11.5-6
- 受入基準 AC-084: 1024×720、760×600、200% 表示の各条件で、全パネルに到達でき、横スクロールが出ない。元のサイズに戻すと保存したレイアウトに戻る。

#### NFR-UX-009 ペルソナ別の既定レイアウト
- 要求: 各 step の既定のレイアウトは、§5.1 の表の「既定のレイアウト」に従う（P-01 は「4 結果」、P-02 は「2 採点設計」と設定の「通常評価」、P-03 は「3 実行」と「4 結果」の cost・ログ）。複数のペルソナに当てはまる利用者の既定は FR-065 に従う。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD｜上位: CON-UI-02｜出典: §5.1、SRC-005、SRC-007、SRC-008
- 受入基準 AC-085: ペルソナ P-01 を選んだ利用者が初めて「4 結果」を開くと、左に結果一覧、中央に詳細、右に分布・ヒートマップ・類似度一覧のタブが表示される。

#### NFR-UX-010 OS の表示設定への追従
- 要求: アプリは OS のライト／ダーク、ハイコントラスト、文字サイズ、視覚効果（アニメーション）の設定に従って表示する。アプリ独自のテーマ切替の UI は設けない。
- 状態: 承認済み（Q-009 2026-10-06）／利用者決定｜優先度: SHOULD（視覚に制約のある利用者が OS 側の設定で読めるようにするため）｜上位: CON-UI-01、NFR-A11Y-001｜出典: SRC-009（Fluent 2。外部確認未実施）
- 関連: 草案 §11.5-10「高 contrast・theme 切替は追加しない」は「アプリ独自の切替 UI を作らない」意味と解し、OS の設定への追従とは両立させる（Q-009 2026-10-06）
- 受入基準 AC-086: Windows のハイコントラストを有効にして起動すると、全 step の文字・枠・focus が OS のハイコントラスト色で表示され、状態が色以外でも区別できる。

### 8.2 ペルソナ別の情報表現

#### FR-065 ペルソナの選択と既定の表現
- 要求: 利用者は、自分に当てはまるペルソナ（P-01〜P-03、複数可）を選べ、選んだペルソナの既定の表現とレイアウトが使われる。初回の既定は P-01 とする。複数を選んだ場合は、各 step で最初に選んだペルソナのうち、その step に既定の表現を持つものを使う。利用者は許可された範囲（§5.1 の各ペルソナの表現）で表現をいつでも切り替えられる。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD｜上位: CON-UI-02、G-001｜出典: §5、SRC-001 §2.1
- 期待する価値: 役割に合った見方が最初から出る。負担・副作用: 選んだペルソナは NFR-UX-004 の `layout.json` に保存する（承認依頼の推奨どおり。DR-013）。FR-040 の `setting.txt` は変えない。確認方法: 下記 AC。
- 受入基準 AC-087: P-02 と P-03 を選んだ利用者が「2 採点設計」を開くと P-02 の既定が、「3 実行」を開くと P-03 の既定が表示される。

#### FR-066 採点担当教員の結果表現（分布・ヒートマップ・類似度一覧）
- 要求: 「4 結果」で、P-01 は結果一覧と詳細に加えて次を使える。(1) `Final_Score` の分布ヒストグラム（区間の件数、空欄の件数を別に表示）。(2) 学生行×設問の得点率（`Question_Earned ÷ Points`）のヒートマップ（空欄は技術的失敗として別の記号）。(3) 設問ごとの類似度の降順一覧（参照回答との類似度・減点・他学生との最大類似度と相手行。「類似度は不正行為の証明ではない」旨を常に表示）。ネットワーク図は使わない。
- 状態: 承認済み（Q-004 2026-10-06。最初の版で導入）／利用者決定｜優先度: SHOULD（クラス全体の偏りと外れ値を見つけ、詳細で確かめる行を選びやすくする）｜上位: CON-UI-02、G-001、G-002｜出典: SRC-005、SRC-006、SRC-001 §7.5、§17.2
- 関連: FR-045（ヒートマップは結果一覧とは別のタブに置き、一覧の 5 列は変えない。Q-004）、FR-052、FR-070、NFR-SEC-006
- 受入基準 AC-088: 530 行の結果で、ヒストグラムの区間の件数の合計 + 空欄の件数が 530 と一致する。ヒートマップのセルを選ぶと、その行の詳細が開く。類似度一覧に注意書きが表示される。

#### FR-067 評価設計担当の配点構成の表現
- 要求: 「2 採点設計」で、P-02 はベース点・固有設定配点・各設問配点の積み上げ棒（合計 100 の基準線と差分の数値付き）を使える。評価項目別の点の分布は FR-072 に分けたが、廃止した（依頼 2026-10-06）。
- 状態: 承認済み（Q-004 2026-10-06。最初の版で導入）／利用者決定｜優先度: SHOULD（合計 100 の内訳の誤りを見つけやすくする）｜上位: CON-UI-02、G-002｜出典: SRC-007、SRC-001 §6
- 関連: FR-012、FR-070
- 受入基準 AC-089: 設問配点の合計が 100 に 0.5 足りない定義で、積み上げ棒に差分 −0.5 が数値で表示され、FR-012 の検証エラーと同じ値になる。

#### FR-068 保守エンジニアの実行表現（attempt のタイムライン）
- 要求: 「3 実行」と「4 結果」で、P-03 は attempt 単位のタイムライン（横軸は時刻、行は評価単位、終端結果を記号と文字で表示、再試行は同じ行に並べる）とログ表を使える。タイムラインは job log と同じ情報（数値・生成 ID・閉じた code）だけを使い、本文を表示しない。
- 状態: 廃止（依頼 2026-10-06）。Q-004 で保留後、利用者が「やりません」と決定／AI提案｜（廃止のため優先度なし。旧: MAY）｜上位: CON-UI-02、G-004｜出典: SRC-008、SRC-001 §11.9
- 廃止の理由: 利用者が除外を決定（2026-10-06）。P-03 の既定の表現は、cost 要約とログ表（FR-043）とする（§5.1）。コード・テスト・カタログの行がなくなった時点で本文から外す
- 受入基準 AC-090: rate limit で再試行した評価単位が、同じ行に 2 つ以上の attempt として表示され、各 attempt の終端結果がログ表の値と一致する。

#### FR-069 表現どうしの連動
- 要求: 同じデータの異なる表現（一覧・詳細・ヒストグラム・ヒートマップ・類似度一覧・積み上げ棒・ログ表）の間で、選択中の行・設問・絞り込み・期間が連動し、表現を切り替えても保たれる。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD｜上位: CON-UI-02｜出典: CON-UI-02
- 受入基準 AC-091: ヒストグラムで 0〜10 点の区間を選ぶと一覧がその行に絞り込まれ、ヒートマップに切り替えても同じ絞り込みと選択行が保たれる。

#### FR-070 視覚表現の代替手段
- 要求: すべての図（ヒストグラム、ヒートマップ、積み上げ棒）に、同じ情報を理解・操作できる代替（数値の表、件数・平均・中央値・最小・最大・空欄件数のテキスト要約、キーボードでの要素の移動と選択、支援技術での読み上げ）を用意する。状態や値を色だけで示さない。表示の更新は読み上げで通知する。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: MUST（図を採用する場合。支援技術の利用者を排除しないため）｜上位: CON-UI-02、NFR-A11Y-001｜出典: SRC-004（SC 1.4.1、2.1.1、4.1.3）
- 受入基準 AC-092: ヒートマップをキーボードだけで移動でき、各セルで「行・設問・得点率」が読み上げられる。表の代替表示の値が図と一致する。グレースケールでも状態を区別できる。

#### FR-071 表現が成り立つデータの条件と代替
- 要求: 各図は、表示に必要なデータの条件を満たさないとき、空の図を出さずに理由と代替を示す。条件: 結果の図は完了または一部完了の run があること、配点構成は評価定義があること。最大 20,000 行・設問数の上限なしでも表示でき、ヒートマップは縦に virtualization する。速報値（FR-046）の表示中は図を「暫定」と明示する。図は追加の AI 送信・ファイル保存を起こさない。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: SHOULD｜上位: CON-UI-02、NFR-PERF-001｜出典: SRC-001 §11.12、§15
- 受入基準 AC-093: run 前に「4 結果」の図を開くと「結果がありません」と理由が表示される。20,000 行×20 設問のヒートマップで UI が応答し続ける。

#### FR-072 評価設計担当の評価項目別の点の分布
- 要求: 「2 採点設計」で、前回 run がある場合に、P-02 は評価項目別の raw の分布（空欄を除いた件数と、空欄の件数を表示）を使える。前回 run がない場合は「前回の結果なし」と示す。
- 状態: 廃止（依頼 2026-10-06）。Q-004 で保留後、利用者が「やりません」と決定／AI提案｜（廃止のため優先度なし。旧: SHOULD）｜上位: CON-UI-02、G-002｜出典: SRC-007
- 廃止の理由: 利用者が除外を決定（2026-10-06）。P-02 の既定の表現は、設問タブ・編集フォーム・配点構成（FR-067）とする（§5.1）。コード・テスト・カタログの行がなくなった時点で本文から外す
- 受入基準 AC-096: 前回 run がある定義で、評価項目ごとの分布の件数の合計 + 空欄の件数が、前回 run の対象行数と一致する。前回 run がない場合は「前回の結果なし」と表示される。

#### NFR-SEC-006 ペルソナ表示はアクセス制御ではない
- 要求: ペルソナと表現の切替は利便性のためであり、アクセス制御ではない。どの表現でも、選択していない列（氏名など）と、現在の run・入力の範囲外の情報を表示しない。
- 状態: 承認済み（承認依頼 2026-10-06）／AI提案（利用者が承認）｜優先度: MUST（図を採用する場合。学生情報の露出を増やさないため）｜上位: CON-UI-02、G-003｜出典: CON-UI-02、SRC-001 §23 A-RV-01
- 受入基準 AC-094: 氏名列に canary 文字列を入れた run で、どのペルソナ・どの表現でも canary が画面・読み上げ名・ToolTip に 0 件。

- 最良と考える選択: A
- その選択が最良である理由: どちらも草案で「公開しない」「機構・静的契約の検証だけ」と限定されており（SRC-001 §13.2-6、§13.4）、教員の採点（G-001）にも 1 操作起動（G-005）にも直接寄与しない。後から追加しても元に戻しやすい。残るリスクは、将来 macOS を対応にするときの準備が遅れること。
- 回答までの扱い: FR-059・FR-060 を承認済み・MUST のまま残し、後続の実装は FR-055〜FR-058 を先に行う。

#### Q-008 再実装の目的と成功指標の目標値（回答済み）
- 回答: A（最良と考える選択どおり。2026-10-06、要求所有者。決定記録 DR-011）
- 質問事項の詳細な説明: 前版は 0.8.6 が公開済みで（SRC-002）、今回の依頼は同じ要求を本リポジトリで実装すること。再実装の理由と、G-001 の目標値（採点の手間をどれだけ減らすか）は、依頼・草案・前版にない。社内情報は確認できなかった（Work IQ 未認証）。このため事業妥当性（§2.5）が「条件付き」に留まる。
- 妥当な選択肢:
  - A: 目的を「前版の機能を保ったまま、管理データ（本書とカタログ）を正本にして保守できる実装へ作り直すこと」とし、G-001 の指標を「同じ見本で、教員の操作数と AI 待ちを除く処理時間が前版以下」とする。影響: 前版との比較で判定でき、測定が容易。
  - B: 目的は A と同じで、G-001 の指標を「1 課題（530 行）の採点にかかる教員の時間を、手作業の採点より X% 減らす」とし、X を利用者が決める。影響: 事業効果を直接測れるが、手作業の基準時間の測定が要る。
  - C: 成功指標を定めない。影響: 作業量最小。事業妥当性を判定できない。
- 最良と考える選択: A
- その選択が最良である理由: 前版という比較対象が既にあり、同じ見本で測れば追加の調査なしに判定できる。再実装の価値（保守性）は、要求 ID からコードとテストを引ける状態（FR-064）で確認できる。利用者の目的が別にある場合は自由記述で教えてほしい。
- 回答までの扱い: G-001 の目標値を TBD とし、事業妥当性を「条件付き」とする。

#### Q-009 OS の表示設定（ダーク・ハイコントラスト・文字サイズ）への追従（回答済み）
- 回答: A（最良と考える選択どおり。2026-10-06、要求所有者。決定記録 DR-012）
- 質問事項の詳細な説明: UX の観点から、OS の設定（ライト／ダーク、ハイコントラスト、文字サイズ、動きの軽減）に従うことを NFR-UX-010 として提案した。草案 §11.5-10 は「高 contrast・theme 切替は追加しない。既存 FluentTheme を使用する」と定めている。これが「アプリ独自の切替 UI を作らない」意味か、「OS のハイコントラストにも追従しない」意味かは草案から判断できない。
- 妥当な選択肢:
  - A: アプリ独自の切替 UI は作らず、OS の設定（ダーク、ハイコントラスト、文字サイズ、動きの軽減）には追従する。影響: 草案の「切替 UI を作らない」と両立する。試験と色の調整が増える（中）。
  - B: 草案どおり既存のテーマだけを使い、OS の設定にも追従しない。影響: 作業量最小。ハイコントラストを使う利用者が読みにくい。
  - C: OS のハイコントラストと文字サイズだけに追従し、ダークには追従しない。影響: アクセシビリティ上重要な部分だけを満たし、作業量を抑える。
- 最良と考える選択: A
- その選択が最良である理由: OS 設定への追従は利用者が既に持つ設定を尊重するもので、草案が除外した独自のテーマ切替とは別物と解釈できる。視覚に制約のある教員を排除しない。残るリスクは、草案の意図が B だった場合と、ダーク対応の色の調整費用。
- 回答までの扱い: NFR-UX-010 を承認待ちとし、後続の実装は草案どおり既存のテーマを使う。
